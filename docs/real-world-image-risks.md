# 真实多轮生图的边界与风险

## 1. 三层一致性不能混为一谈

真实系统同时存在三份事实：

```text
用户真正想要的内容
        ↓ 可能理解错误
Agent 当前维护的需求与 Prompt
        ↓ 可能执行错误
图片模型最终生成的像素
```

本项目主要解决第一条连接：让用户表达、当前规格和 Prompt 尽量一致。即使这部分完全正确，图片模型仍可能没有执行某项要求。

因此每项约束至少需要区分：

| 状态 | 含义 |
|---|---|
| requested | 用户是否提出或确认了要求 |
| prompted | 要求是否进入本次生成指令 |
| attempted | 生成流程是否尝试执行 |
| verified | 最终图片是否被验证满足 |
| accepted | 用户是否接受该结果 |

`prompted=true` 绝不能自动推导出 `verified=true`。

## 2. 需求理解层的边界

### 2.1 指代不清

“把它改红一点”可能指瓶身、背景、Logo 或灯光。历史中存在多个候选对象时，系统必须澄清，不能依赖模型猜测。

### 2.2 否定和作用域

以下表达容易被模型读反：

```text
不要把背景改成黑色，改成浅灰。
除了标签以外，其他都可以调整。
不是不要文字，只是不要新增文字。
```

解析器需要表达否定的目标和作用范围，而不是只抽取关键词。

### 2.3 改口、撤销和反向约束

“允许加文字”可能有两种数据语义：

```text
remove(text.addition=forbidden)
set(text.addition=allowed)
```

前者恢复自由状态，后者建立新的显式要求。产品必须先定义语义，不能把选择交给 LLM。

### 2.4 字段粒度

“光线暖一点”只应修改色温，不应覆盖方向和柔和度。字段过粗会导致局部修改误删信息；字段过细又会把创作过程变成复杂表单。

### 2.5 父子级冲突

```text
产品外观全部不变
Logo 换成新的圆形 Logo
```

两项位于不同字段，但可能语义冲突。生产系统需要字段层级、保护区域和领域规则，不能只比较完全相同的路径。

### 2.6 主观要求不可精确验证

“高级”“松弛”“有呼吸感”“不要太商业”没有唯一标准。它们应该保留为开放意图，并允许用户通过候选图选择，而不是伪装成精确布尔值。

### 2.7 多 Skill 冲突

两个 Skill 可能分别建议：

```text
电商摄影 Skill：白底、居中、清晰展示产品
杂志大片 Skill：环境化背景、偏心构图、戏剧阴影
```

真实产品需要定义 Skill 的作用范围、优先级、是否可组合，以及 Default、Suggestion、Guardrail 之间的冲突规则。

### 2.8 Skill 版本漂移

如果会话开始时使用 `skill@1.0`，中途 Skill 升级到 `1.1`，历史版本不能悄悄改变。每个作品 Revision 应锁定 Skill ID、版本和配置摘要。

### 2.9 长对话压缩

LLM 上下文会被截断或总结。不能依赖完整聊天历史恢复当前状态；结构化 Revision 才是事实来源，聊天只作为审计和重新解释的证据。

### 2.10 并发修改

用户在两个浏览器窗口同时修改同一作品时，最后写入可能覆盖另一个窗口。需要 revision number、乐观锁和合并冲突，而不是无条件保存。

## 3. 真实多轮图片生成的问题

### 3.1 身份和产品外观漂移

即使每轮都写“其他不变”，人物面部、瓶身轮廓、材质、Logo 位置和标签排版仍可能逐渐变化。语言约束无法提供像素级保持保证。

建议：

- 保存原始主体和遮罩；
- 优先在原始高质量素材上做局部编辑；
- 使用专门的 Subject Reference 或一致性模型；
- 对关键区域进行图像相似度、OCR 或特征比较；
- 不要把每轮生成结果无限作为下一轮唯一输入。

### 3.2 累计画质退化

如果流程是：

```text
image_v1 → 编辑成 v2 → 编辑成 v3 → 编辑成 v4
```

每一轮都可能重新编码和重绘，导致细节变糊、纹理塑料化、文字失真和边缘污染。多轮一致性提高不代表没有累计损失。

更可靠的方式是保存：

```text
原始资产 + 已接受的编辑操作 + 遮罩 + 当前合成结果
```

必要时从原始资产重新应用编辑，而不是永远从最后一张生成图继续生成。

### 3.3 “保持颜色”与“改变光线”天然耦合

用户可能同时要求瓶身颜色完全不变和光线明显变暖。但真实摄影中，暖色光会改变瓶身在像素上的观测颜色。

系统需要澄清保持的是：

- 产品固有色；
- 感知上的品牌色；
- 指定区域的 RGB/色差范围；
- 还是仅不主动重新设计瓶身颜色。

否则验证器无法给出可信结论。

### 3.4 Logo、标签和文字容易被重绘

图片模型经常生成近似但错误的文字、字符和品牌标识。Prompt 中写“完全不变”并不足够。

生产流程更适合：

- 将 Logo 和标签作为受保护图层；
- 生成时遮罩保护；
- 生图后重新合成原始品牌资产；
- 用 OCR、模板匹配或像素比较验收；
- 关键品牌资产失败时禁止自动发布。

### 3.5 局部编辑越界

遮罩或选区并不一定精确。编辑背景时可能侵入产品边缘、玻璃反射或头发区域；编辑衣服时可能改变人物手部和身体比例。

每次局部编辑应记录：

- 用户选区；
- 自动扩张后的实际遮罩；
- 保护区域；
- 模型实际输入尺寸；
- 边缘羽化和合成策略。

### 3.6 构图变化会连带改变其他属性

把主体从居中改为三分构图，可能要求补全背景、改变相机视角或重新生成遮挡区域。因此“只改构图”在像素层不一定是局部操作。

系统应区分：

- 可以通过裁切/位移完成的确定性编辑；
- 必须扩图或重绘的生成式编辑；
- 会影响产品身份的高风险编辑。

### 3.7 参考图角色污染

即使声明 `image_B` 只参考光影，模型仍可能复制它的背景、物体、色彩或文字。这是模型行为问题，不是状态字段本身可以完全阻止的。

更安全的流程是：

1. 单独分析 image_B，提取结构化光影描述；
2. 人工或程序确认描述；
3. 最终生图只传递光影描述，不直接传递 image_B；
4. 如果必须传图，生成后检查是否出现内容污染。

### 3.8 多参考图权重不可解释

主体参考、风格参考、构图参考和光影参考同时存在时，模型可能自行权衡。即使 API 提供权重，不同模型版本对权重的解释也可能不同。

需要记录模型、版本、权重和参考图顺序，并通过评测确定合理范围。

### 3.9 尺寸、裁切和宽高比漂移

修改宽高比可能裁掉 Logo、扩大背景、改变主体相对大小或触发整图重绘。“内容不变，只改比例”通常无法字面满足。

应先尝试确定性裁切和画布扩展，再决定是否需要生成式补全。

### 3.10 随机性与不可复现

同一个 Prompt、同一组参考图也可能产生不同结果。服务端模型升级后，即使保留 seed，也不一定完全复现。

每个图片 Revision 应记录：

- 模型与模型版本；
- Prompt 和负面约束；
- seed（如果支持）；
- 参考素材 ID、哈希、顺序和权重；
- 遮罩和尺寸；
- Skill ID 和版本；
- API 参数与生成时间。

### 3.11 安全策略可能造成静默偏离

生成服务可能因为安全策略修改、拒绝或弱化部分请求。系统不能把“API 返回了一张图”视为完整成功，应区分：

```text
生成完成
部分执行
被安全策略修改
拒绝生成
技术失败
```

### 3.12 成本和延迟

生成、重试、验证和多候选比较都会增加成本。每个用户修改都立即重新生图可能体验很差。

可以先更新规格并展示 diff，让用户确认后再生成；低风险确定性操作则直接执行。

## 4. 验证也不是绝对真相

建议为每项要求建立验证结果：

```text
passed          自动验证通过
failed          自动验证失败
uncertain       证据不足或模型判断不稳定
not_verifiable  当前系统无法自动验证
```

适合自动检查的内容：

- 宽高比和尺寸；
- 是否存在明显文字；
- 背景的大致颜色；
- Logo/标签区域是否发生较大变化；
- 主体是否缺失。

不适合给出绝对结论的内容：

- 是否“更高级”；
- 是否完全忠于某种风格；
- 暖光下品牌颜色是否“保持不变”；
- 人物身份是否在所有细节上完全一致。

视觉 LLM 也是概率模型，不应该成为唯一验收者。高风险品牌资产需要确定性比较或人工批准。

## 5. 推荐的真实生成事务

一次用户修改不应直接覆盖当前作品，而应经历：

```text
1. Parse
   用户消息 → 候选 ChangeSet

2. Validate
   检查字段、来源、冲突和待澄清问题

3. Commit spec
   保存新的需求 Revision，但尚不替换已接受图片

4. Plan
   判断使用确定性编辑、局部生成、整图生成还是重新合成

5. Generate candidate
   产生新的候选图片版本

6. Verify
   对每项硬约束输出证据和验证状态

7. Accept
   用户接受后，候选图片才成为新的 active image revision
```

如果生成或验证失败：

- 新的需求 Revision 可以保留为“待生成”；
- 上一张已接受图片继续可用；
- 失败候选不应覆盖 active image；
- 用户可以重试、修改要求或回到之前分支。

## 6. 版本模型建议

需求版本和图片版本应分别维护：

```text
Spec Revision 4
├── Image Candidate 4A — failed: label changed
├── Image Candidate 4B — uncertain: logo similarity
└── Image Candidate 4C — accepted

Spec Revision 5
└── generation pending
```

这能避免“状态更新成功”和“图片生成成功”被错误地绑定成同一件事。

## 7. 上线前需要补充的评测

当前 20 个文本对抗测试只是开始。真实系统至少还需要：

- 每个用例重复运行，测量 LLM 输出方差；
- 独立人员编写的隐藏测试集；
- 50～100 轮长会话测试；
- 两个以上 Skill 的组合与冲突；
- 中英文、口语、错别字、语音转写输入；
- Prompt injection 和引用文本隔离；
- 并发修改和 Revision 冲突；
- 不同图片模型的多轮画质与身份漂移测试；
- Logo、标签、文字和产品颜色的量化验证；
- 模型升级前后的回归评测；
- 成本、延迟、失败率和人工确认率。

## 8. 当前方案最诚实的能力声明

当前原型可以说：

> 系统以事务方式维护多轮创作要求，追踪用户、Skill 和素材角色，并在可检测冲突出现时保护上一版有效状态。

当前原型不能说：

> 系统保证最终生成图片满足所有要求。

后者必须依靠真实生图链路、逐项验证、版本分支和人工验收共同完成。
